**codegen** turns one annotated C++ declaration into as many artifacts as you need, in as many languages as you need. Annotate a struct once, and a single run emits its C++ serialiser, the matching TypeScript interface, an SQL migration, and a reference page — from one source of truth, all regenerated together when that struct changes.

That fan-in is the point. Generating `toString()` for an enum is the hello-world, and if that's all you need, [`magic_enum`](https://github.com/Neargye/magic_enum) is one header and you should use it. What a header-only library can't do is route sixty annotated types across four output files in three languages, inject declarations back into the original header, or let you write the transformation as a script you can unit-test without a compiler.

You write a Luau script that receives a structured AST node as JSON and returns text. The engine handles parsing, semantic analysis, scheduling, deduplication, file routing, and inline injection.

It ships as a single binary. Generation opens no sockets — [no licence check, no telemetry, no call home](/trust/no-call-home/). It runs the same on every machine.

</div>

## How codegen is built

codegen separates the problem into two clean layers:

1. **Analysis** — handled by the engine. The full C++ AST is resolved and serialised to JSON (namespaces, template arguments, member variables, enumerators, annotations), and on top of it the engine builds a real semantic model: a symbol database, class hierarchy, dependency graphs, and resolved types.
2. **Transformation** — handled by you, in LuaU. Your rule receives one AST node as JSON and returns output text — and can query the semantic model on demand (resolve a field's type to its declaring symbol, look up references, walk base classes). The rule has no compiler coupling, no filesystem access, and no network access.

This split is what makes everything below possible.

## Core capabilities

<CardGrid>
  <Card title="Cross-language generation">
    Rules emit text. The engine does not care whether that text is C++, TypeScript,
    Markdown, SQL, or a JSON manifest. One annotated C++ type can drive a serialiser,
    an FFI binding, a documentation page, and a database migration — all from the
    same source of truth.
  </Card>
  <Card title="Non-1:1 generation">
    Most generators emit one output file per input file. codegen does not require this.
    A `grouping.luau` script routes each matched entity to any output path — fan-in
    dozens of structs into a single `api-reference.md`, a `registry.cpp`, or a sorted
    `bindings.ts`. The topology is yours to define.
  </Card>
  <Card title="Deterministic output">
    Same source ⇒ same output. Always. The engine is a pure function over your AST.
    Generated files are stable across machines and CI runs, making diffs meaningful
    and code review tractable.
  </Card>
  <Card title="LLM-ready AST schema">
    The C++ AST is fully serialised as JSON before any rule sees it. Rules are testable
    without a compiler, inspectable with `jq`, and the full docs are also published as
    a single plain-text bundle at [`/llms-full.txt`](/llms-full.txt) — drop it into any
    LLM agent for codegen-aware code intelligence.
  </Card>
  <Card title="Semantic-aware rules">
    Rules see more than syntax. A [semantic query API](/concepts/semantic-query/) resolves
    a field's type to its declaring symbol, pivots into that type's own AST, and looks up
    references, base classes, and members — the same analysis that powers the LSP and MCP
    servers. Generate against what your types *mean*, not just how they're spelled.
  </Card>
  <Card title="Workspace-cache acceleration">
    codegen connects to the [workspace daemon](/integrations/cli/) on every run — there's no
    flag to opt in or out. AST subtrees and semantic queries are served from the shared
    workspace intelligence cache, and types resolve against a whole-workspace snapshot for
    accurate cross-header resolution. The daemon must already be serving `--workspace-dir`
    (defaults to the current directory).
  </Card>
  <Card title="Rules testable in isolation">
    Feed a JSON blob to a rule, assert on the output. No compiler, no project, no fixtures.
    The same property that makes rules LLM-friendly makes them unit-testable in seconds.
  </Card>
  <Card title="Isolated execution">
    LuaU runs in a sandboxed VM. Rules have no filesystem access and no process
    spawning — neither is grantable. Network access is the one escape hatch, and only
    for hosts you allowlist in the config. A malicious rule in a third-party library
    cannot exfiltrate your source code.
  </Card>
  <Card title="Inline injection">
    Rules can emit a `source` (to a `.g.cpp` file) and an `inline` list — declarations
    injected back into the original header at a designated anchor comment. Bare anchors
    are rewritten into idempotent `:begin]] / :end]]` blocks on first run.
  </Card>
  <Card title="Self-hosted">
    codegen generates parts of its own infrastructure. We use it ourselves to build it,
    so every feature you rely on has already been exercised against a 150k+ LoC
    real-world codebase.
  </Card>
</CardGrid>

## What codegen does not do

Deliberate boundaries, worth knowing before you invest in a rule:

- **No template instantiation.** A rule sees the template as written. Written template
  arguments are extracted syntactically, but no specialization is synthesised, and an
  uninstantiated generic resolves to a `dependent` type.
- **No `constexpr` folding.** Constant values are carried as their source text; the
  engine never evaluates them.
- **No overload ranking.** Overloads are indexed distinctly, but the engine will not
  pick the single best-viable candidate for a call site the way a compiler front-end does.
- **No self-contained parse.** Every run connects to the workspace daemon for its
  project root. If nothing is serving that root, the run fails rather than falling back.

If your generator needs to reason about instantiated templates or fold constant
expressions, codegen is the wrong tool and will stay the wrong tool.

## What about C++26 reflection?

P2996 static reflection is in C++26, and for a large share of what codegen does *in
C++* it will simply be better: it's in the language, there's no external process, and
there are no generated files to check in.

It does not cover the same ground, though. Reflection emits C++ — it cannot emit the
TypeScript interface, the SQL migration, or the Markdown page that one annotated type
drives here, and anything crossing out of the translation unit still needs a generator.
And it needs a toolchain that implements it: outside experimental forks, mainstream
compiler support is still arriving, so it isn't a 2026 answer for a codebase that has
to build on the compilers it has today.

The two aren't rivals. Reflection replaces the in-C++ half of this; the cross-language
fan-in half doesn't go away.
