## Distribution model

CodeXX DTDK is distributed as **independently versioned components** on GitHub Releases. You install and update them through the **DTDK Manager**, which downloads each component, verifies it, and stages it into a versioned, side-by-side layout under `~/.codexx`.

There is no system package manager, no `npm install`, no Python environment to configure, and no install-time script running with elevated privileges. Each component archive is a self-contained, relocatable FHS tree (`bin/`, `lib/`, `include/`) — moving the install root never breaks library resolution.

## Every release is attested

Each component release is a four-part **Package Bundle**: the binary archive, an SPDX SBOM, a SLSA Build L3 provenance record, and a Sigstore signature bundle — plus a SHA-256 sidecar on the archive. The release pipeline structurally rejects incomplete bundles.

The manager verifies the SHA-256 of every archive before it installs it; full Sigstore signature verification is available on demand.

## Build-time dependencies

The build-time dependency tree is pinned end to end:

| Source | Pinned by |
|---|---|
| vcpkg ports (tree-sitter-cpp, luau, abseil, nlohmann-json, …) | `vcpkg.json` plus the vcpkg baseline commit; resolved versions captured under `vcpkg_installed/` |
| Vendored submodules (`vendor/*`) | exact commit SHAs in `.gitmodules` / the recorded submodule state |

No dependency is fetched from a mutable tag or branch. The SBOM shipped with each release (`.spdx.json`) inlines every resolved vcpkg per-port package and every `vendor/*` submodule SHA, so the bill of materials reflects exactly what was linked.

## What the release pipeline actually does

Every published archive goes through these steps:

- **Symbol stripping** — binaries are installed with `cmake --install --strip`, so internal symbols are not shipped.
- **SPDX SBOM** — generated with Microsoft `sbom-tool`, then post-processed to inline every resolved vcpkg per-port package and every `vendor/*` submodule SHA.
- **SHA-256 sidecar** — each archive ships a `.sha256` next to it; the SBOM gets one too.
- **Sigstore keyless signing** — each archive is signed with `cosign` under GitHub OIDC, producing a detached `.sigstore` bundle recorded in the public Rekor transparency log.

Two things this pipeline does **not** do yet, which you should know before trusting a binary:

- **No Authenticode signature on Windows builds.** Verify the `.sigstore` bundle instead.
- **No Apple notarization**, and no macOS archives are published at all today — macOS support is [coming soon](/getting-started/installation/). Build from source on macOS in the meantime.

## Why this shape

- **No dependency confusion** — there is nothing to resolve at install time; the manager pulls exact, attested archives.
- **No install-time code execution** — extraction places files; it does not run scripts.
- **Pre-extraction verification** — the detached `.sigstore` and `.sha256` siblings let you verify an archive before unpacking it.
- **Auditable** — every release signature is recorded in the public Rekor transparency log.

## Third-party rules are a different question

Everything above concerns the components CodeXX ships. Rules published to the [rules registry](/rules/registry/) are the one place third-party code enters your build, and they are governed differently — deliberately so.

A rule is not fetched, resolved, or installed. You clone or copy a directory of Luau text into your own repository, where it is versioned alongside your code and visible in every diff. There is no resolution step, so the dependency-confusion class of attack has nothing to attach to, and there is no install-time execution because there is no install.

Two controls sit either side of that:

- **At publication** — rules land only through pull requests reviewed by a maintainer. A rule requesting network or environment access is labelled and blocked until that request is justified. Publishing is intentionally not self-service.
- **At execution** — a rule runs inside the [Luau sandbox](/rules/luau-sandbox/), where network and environment access are opt-in per rule and declared in `config.yaml` — filesystem access is not available at all, granted or otherwise. See the [Permissions Model](/rules/permissions/).

Neither control substitutes for reading the rule. Review is what raises the floor; the code still runs on your machine, during your build, and it is a few dozen lines you can read in a minute.

<Alert type="info" title="Key Takeaways">
- Components are distributed as independently versioned, attested archives and installed through the DTDK Manager — no system package manager, no privileged install scripts.
- Build-time dependencies are fully pinned (vcpkg ports plus vendored submodule SHAs) and enumerated in a shipped SPDX SBOM.
- Releases are stripped, SBOM'd (SPDX), checksummed, and Sigstore-signed. There is no Authenticode signature yet, and no macOS archives yet.
- Every archive carries a SHA-256 sidecar and a Sigstore bundle; the manager verifies checksums automatically.
- Registry rules are vendored, not resolved — reviewed at publication, sandboxed at execution, and yours to read before you run them.
</Alert>
